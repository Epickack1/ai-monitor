# AIMonitor

Консольное приложение для отслеживания доступности моделей искусственного интеллекта в сервисе OpenRouter.

## Назначение

OpenRouter даёт доступ к сотням моделей ИИ через единый API, но каждую модель обслуживают разные провайдеры, и любой из них может работать с перебоями. AIMonitor показывает, какие из выбранных моделей сейчас доступны, сколько провайдеров у каждой работает и каков их аптайм. Так перед подключением модели к своему проекту видно, стоит ли на неё рассчитывать.

## Целевая аудитория

- Разработчики, которые используют модели ИИ через OpenRouter в своих приложениях.
- Студенты и исследователи, которые выбирают модель, в том числе бесплатную.
- Администраторы сервисов с ИИ, которым важно заранее узнавать о сбоях моделей.

## Предметная область

Мониторинг доступности моделей ИИ. OpenRouter публикует каталог моделей и для каждой модели список провайдеров: их статус и процент времени без сбоев (аптайм) за последние 5 минут, 30 минут и сутки. На основе этих данных приложение определяет состояние модели. Дополнительно, при наличии API-ключа, модель можно проверить живым запросом с замером времени ответа.

## Основные сущности

- **Модель** — id в OpenRouter (например, `openai/gpt-4o-mini`), название, цена, признак бесплатной модели.
- **Провайдер** — компания, которая обслуживает модель: статус работы, аптайм за 5 минут, 30 минут и сутки.
- **Результат проверки** — итоговый статус модели: «Доступна», «Нестабильна», «Недоступна» или «Не найдена».
- **Список отслеживания** — модели, выбранные пользователем для регулярной проверки.
- **История проверок** — результаты всех проверок: модель, статус, аптайм, время.

## Основные функции

1. Проверка доступности всех отслеживаемых моделей со сводкой.
2. Подробная проверка одной модели с таблицей всех её провайдеров.
3. Просмотр списка отслеживаемых моделей с результатом последней проверки и сортировкой по названию или по аптайму.
4. Поиск модели в каталоге OpenRouter, в том числе только среди бесплатных.
5. Добавление модели в отслеживание и удаление из него.
6. Живой тест модели: короткий запрос и замер времени ответа (нужен API-ключ).
7. Сохранение каждой проверки в историю (`data/history.json`).
8. Статистика доступности по истории: число проверок, доля успешных, средний аптайм, самая стабильная и самая проблемная модель.
9. Просмотр последних проверок выбранной модели.

Все данные сохраняются в JSON-файлах и загружаются при запуске. Некорректный ввод, отсутствующий или повреждённый файл данных не приводят к аварийному завершению программы.

## Как определяется статус модели

| Статус | Условие |
|---|---|
| Доступна | есть работающий провайдер, аптайм лучшего из них за 5 минут не ниже 90% |
| Нестабильна | провайдеры работают, но аптайм ниже 90% |
| Недоступна | ни один провайдер не работает |
| Не найдена | модели нет в OpenRouter или нет связи с сервисом |

Провайдер считается работающим, если OpenRouter сообщает для него статус `0`; отрицательный статус означает сбой.

## Формат данных

`data/watchlist.json` — список отслеживаемых моделей:

```json
[
  {
    "id": "openai/gpt-4o-mini",
    "name": "OpenAI: GPT-4o-mini"
  }
]
```

`data/history.json` — история проверок. `uptime` — лучший аптайм работающих провайдеров за 5 минут (при отсутствии данных — за 30 минут), `null`, если данных нет. Хранится не более 1000 последних записей.

```json
[
  {
    "model_id": "openai/gpt-4o-mini",
    "status": "Доступна",
    "uptime": 99.8,
    "checked_at": "2026-09-26 14:05"
  }
]
```

Записи с неверной структурой при загрузке пропускаются.

## Установка

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Linux / macOS
pip install -r requirements.txt
```

Для живого теста скопируйте `.env.example` в `.env` и впишите ключ с https://openrouter.ai/settings/keys. Остальные функции работают без ключа.

## Запуск

```bash
python main.py
```

## Технологии

- **Python 3** — основной язык
- **urllib** — HTTP-запросы к OpenRouter (стандартная библиотека)
- **json** — хранение списка моделей и истории проверок
- **pytest** — автоматизированные тесты
- **flake8** — проверка оформления кода
- **Git / GitHub** — контроль версий

## План развития

На следующих этапах планируется:

- объектная модель: классы `Model`, `Provider`, `CheckResult`;
- разработка веб-приложения на Django с панелью состояния моделей;
- подключение базы данных вместо JSON-файлов;
- реализация пользователей с личными списками отслеживания;
- разработка REST API для получения статусов;
- уведомления о падении модели;
- контейнеризация приложения в Docker;
- настройка CI/CD.
